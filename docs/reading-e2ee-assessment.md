# Reading and end-to-end encryption

When vault encryption is enabled, Reading notes are encrypted with the vault key like every other note. The same implementation runs on Cloudflare and self-hosted servers. This document describes the implemented boundary.

## Supported workflow

- Obsidian keeps ordinary local Markdown notes. Sync encrypts their contents, including article text, source URLs, tags, reading status and highlights.
- The PWA uses the same recovery code as Obsidian to open the encrypted key bundle locally, remembers the vault keys, decrypts and indexes notes locally, and publishes conditional encrypted note replacements. It supports article viewing, search, favorites, archive, tags, highlights, offline article caching and queued offline edits.
- Browser library, article, draft, outbox and immutable retry records are encrypted. Queued edits retain their exact encrypted requests after a lost response. Recovery preserves damaged records and exports wrapped local-key metadata; explicit logout clears both Reading and Reminders keys and data, while fencing newer enrollments.
- Turning encryption on deletes the server copy, including Reading notes, retained versions, queued captures, operation receipts, derived indexes, extraction jobs and handoffs, then uploads the enabling device's vault encrypted. It refuses to start while saved links are still downloading on the server.
- Destructive encryption reset deletes all seven Reading tables, including enrollment and handoff grants, at the start and completion of the reset.

## Saving articles

Obsidian downloads and extracts articles on the device, on desktop and mobile; its links never reach the server. Browsers cannot read most websites across origins, so an unlocked encrypted PWA sends the link in the body of `POST /reading/encrypted-extract`. The server downloads and extracts the page, returns the article and stores nothing about the request: no D1 row, queue entry, R2 object or log line holds the link or the article. The PWA encrypts the note before committing it. The server therefore sees each link and its public article text while it downloads them; stored notes, URLs and highlights stay encrypted. If the download fails, or article fetching is off and the server refuses it, Crate saves an encrypted bookmark marked unavailable, and **Try again** works on any unlocked device, as in unencrypted vaults. When **Try again** in the web app finds the title of a note that still has its link-based name, the commit renames it: it creates the titled note and removes the old server path in one transaction. This is independent of the deferred Cloudflare browser-rendering feature.

The iPhone Shortcut holds only its capture token. It sends the shared link to the shortcut prepare route. In an encrypted vault, the server downloads the page outside its write lock (unless article fetching is off, when it saves only the link), builds the Reading note and seals it to the vault seal key, whose private half only unlocked devices hold. The server cannot compute name tags, so it commits the note as a new file under a random tag-shaped name in the tagged Reading folder, seals its titled name (`<title> - <site> - <id8>.md`) inside, and shows **Saved** in the Shortcuts sheet. No handoff row, queue entry or log keeps the link or article. Devices open the note immediately under its titled name. Edits re-save it with the vault key and keep its server name; renaming it moves it to the tag of its new name. Until then, a sealed note can be read by anyone holding the vault keys, and a party with server write access could plant new notes in the Reading folder (creates only). Obsidian accepts a sealed note only as a new file: one stored at a server path the device already holds, including an untouched Shortcut note, or named like a note stored at another server path, is skipped and reported as a sync issue, and the local copy is kept. A sealed copy with exactly the bytes the device already holds is accepted, since it changes nothing. Sharing a link twice creates two notes, because the server cannot see the library. The signed template must be published before releasing the app.

Every vault's manifest includes Android's Web Share Target. The service worker keeps a shared link on the device, protected by a non-extractable device-local key even before enrollment, and opens the save form. Before a service worker controls the app, the POST reaches the server, which only echoes the form back into a page that stores it the same way; the server keeps nothing. The web app then saves it like any other link.

## Limits and privacy

File and folder names, including the Reading folder's, are stored as keyed tags. Folder structure, which files are Markdown, sizes, revisions, timing, feature policy and account/session metadata remain visible to the server; see the [protection boundary](e2ee-implementation.md#protection-boundary). Encrypted notes are named after their title and site, as in unencrypted vaults; existing notes keep their names. The PWA trusts the code served by its origin. Websites still see direct download/favicon requests. Local vault files, previous external backups and previously opened devices are not retroactively erased.

The browser accepts at most 10,000 Reading files and 12 MiB of indexed metadata. It retains at most 100 decrypted source notes within a 16 MiB in-memory budget; unchanged metadata is reused without downloading every note on refresh. Persistent article storage is bounded by the 200-article / 50 MiB policy; background copies of new inbox articles use the same encrypted read path and rank below opened articles. Unreadable or duplicate-ID notes are shown as issues. Saving a link waits while any note is unreadable, because that note may already save it; an edit waits only while its own note is unreadable or shares its Reading ID. Waiting changes stay queued and retry. Damaged or future-format offline records stay exportable without blocking healthy articles. If the saved library cannot be decoded, a verified live refresh remains usable with a recovery notice, while the original library and its cached articles remain unchanged.

The Reading and Reminders folders must be separate. Changing either folder needs no re-encryption, because every note uses the vault key; see [moving files and folders](e2ee-implementation.md#moving-files-and-folders). Content-key rotation is not included.

## Verification boundary

All validation uses disposable local D1/R2/DO and desktop browser engines. Hosted D1 writes are zero. Physical iOS/Android offline and background-push acceptance, hosted quotas/CPU checks, and an independent security review remain separate release requirements.
