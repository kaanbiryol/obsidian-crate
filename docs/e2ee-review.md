## Folder connections follow renames

A same-folder rename, including a parent-folder move, now retains scope identity, encryption keys, browser credentials, Reading policy generation and push subscriptions. Each current folder mapping is authenticated with the scope data key. Browser routing follows that binding without replacing its local namespace, drafts or local-state secret. Multiple moves while offline require only the latest authenticated binding. Choosing a different folder in settings changes its access identity and revokes previous connections.

Wire attempts retain their generation. Converted receipts recover accepted saves; once conversion fences the old generation, a missing receipt permits rebuilding an unaccepted attempt with the same semantic operation ID. Reminder revisions remain in the browser's original namespace, preventing a rename from inventing a content conflict. Manual folder-key recovery also retains that namespace and the existing draft key.

The Chromium full Reminders flow passes, including two offline folder moves and recovery of a lost successful reply. Reading follows a rename without another setup link in Chromium and WebKit; native CryptoKey/draft recovery passes both engines. The full WebKit Reminders run still reproduces the previously recorded Settings close/geometry stall before reaching the move scenario. That remains an acceptance limitation, not a passing folder-move test. Hosted D1 writes: **zero**.

The plugin raw-byte budget increases from 5,490,000 to 5,500,000 for about 4.5 KB of additional folder-following code, including embedded Worker/PWA assets. Gzip, Worker and PWA budgets remain unchanged. Filename/folder-name encryption is not part of this change; those paths remain visible. Since E2EE is unreleased, a future private-path format does not need a deployed E2EE-format migration.

## Second-audit fixes and follow-up review

Reviewed and fixed on 2026-10-02. The original ignored reproductions remain under `.generated/e2ee-second-audit/` as historical evidence; maintained regressions now live in the source test suites. Hosted D1 writes: **zero**.

1. **Reading PWA plaintext preflight.** Successful plaintext encryption checks are no longer cached indefinitely. Concurrent checks still share work; the next request verifies current server state before sending its private body. Encrypted sessions retain offline behavior. A failed check keeps requests blocked and displays the connection/unlock error instead of a misleading storage-migration message. Production-browser tests keep a plaintext tab and its private draft open while a real local server conversion enables E2EE, then verify that saving does not transmit the URL.
2. **Durable rename dependencies through conversion.** The folder journal saves preexisting in-memory rename dependencies before stopping the engine. A stopped-engine checkpoint replays filesystem moves, including ordinary file renames received while conversion is paused. Its last applied journal ID is persisted atomically with the manifest, so retries and temporary-checkpoint recovery do not apply nested prefixes twice. Folder-setting changes do not invent filesystem moves. The follow-up review also fixed parent moves overwriting an earlier file rename and round-trip renames leaving a self-dependency that blocked later intentional deletion.
3. **Queued Reading captures across verified moves.** Authenticated address relocation keeps the outbox's original authority and exact request bodies. Folder recovery waits for stopped Reading work and uses a new vault-only receipt read to authenticate legacy plaintext or encrypted captures. It materializes the original bookmark or accepted article locally, preserving article text and highlights; any remote deletion waits for the destination upload. Records remain unchanged until the local note and manifest checkpoint are durable. Recovery caches bounded identity metadata instead of redownloading the library for every queued capture.

The re-audit checked scope/authentication boundaries, converted receipt hashes, missing attempt cleanup, failed disk writes, stale connections, renamed targets, and local/remote divergence. It tightened capture recovery so an unmerged local bookmark cannot authorize deletion of a richer remote article. Expired unconfirmed captures, conflicting copies, and an original article still located outside the selected local Reading folder stop recovery with an explanation and retain the queue and folder journal. They require comparison or moving the original note before resuming; recovery never silently recreates an expired save, overwrites local edits, or discards the original operation.

The architecture remains appropriately separated: cryptographic formats are unchanged; journal parsing, stopped-engine checkpointing, and Reading receipt/materialization each have a focused module. The Worker addition is a read endpoint, with no schema change or background write loop. No new dependency or key-rotation feature was added. The plugin raw-byte budget increased explicitly from 5,480,000 to 5,490,000 bytes for roughly 9 KB of additional recovery code; gzip, Worker, and PWA budgets are unchanged.

## Architecture and code-quality follow-up

The main boundaries are appropriate: `encryption/` owns formats and cryptographic identity, the plugin owns conversion and durable recovery, `sync/` translates ciphertext transport identities into authenticated local metadata, and the two PWA features receive only folder authority. The Worker cannot perform private indexing or extraction. A wholesale rewrite or new general-purpose encryption framework would add risk without improving these boundaries.

The important weaknesses were duplicated enrollment checks, implicit retry state, and treating a server address as the permanent identity of local recovery work. This follow-up implements the following changes:

1. **Prevent plaintext submission from stale, keyless plugin clients.** When another device enables encryption, a previously initialized Reading runtime can still have queued capture URLs. HTTP preflight now checks Reading and Reminders mutations as well as sync/settings before sending their bodies. Server rejection alone was too late to protect the URL. This adds bounded reads for keyless requests, not D1 writes. Existing independent title-lookup protection remains covered.
2. **Reject a downgrade on a fresh encrypted browser link.** Incoming folder-key fragments now count as encryption evidence even before the browser has saved a marker. A null/404 encryption response leaves Reminders locked. Reading and Reminders share scope-state and grant validation, including purpose, path, generation and both key identities. Mismatched grants are rejected before storing keys.
3. **Make folder-setting retries exact and validate saved move targets.** The move journal now saves original and final Reading/Reminders settings before conversion. Retrying a partial settings save cannot turn `Reading/Archive` into `Reading/Archive/Archive`; newer user selections are preserved for explicit recovery. Saved targets must match the current bundle or its exact proposed path change, including secrets and purpose, before they can replace local keys. Older checkpoints remain recoverable. Journal validation and setting mapping live separately from the network workflow.
4. **Cache only authenticated metadata.** An invalid descriptor previously poisoned the in-memory cache and prevented recovery after the server repaired it. Descriptors are now authenticated before caching; subsequent reads reuse verified metadata. Fetches process at most 100 revisions at a time, and the cache stays within 5,000 entries throughout a large inventory. Cached paths remain checked against each requested path.
5. **Unblock encrypted self-hosted address recovery without discarding pending work.** A changing tunnel could strand an unfinished folder move because connection changes were forbidden until the move completed. An authenticated recovery bundle now proves the new address belongs to the same vault, even when conversion advanced local keys before the server accepted them. Credentials and the exact move checkpoint are copied before saving the URL. A local, URL-bound checkpoint scope preserves the original authority of manifests, pending uploads, rename dependencies, local history and content verification. Partial credential/settings failures retain recoverable copies. Other-vault credentials and conflicting destination recovery records are rejected; a different connection or destructive reset clears the retained scope. An unfinished folder conversion continues to block ordinary sync until resumed.

The recovery-bundle comparator is shared as well, so verification includes scope purpose and secrets consistently. Existing lifecycle serialization remains in `SyncRuntime`; format validation and connection preparation remain in focused modules. No new dependency, cryptographic primitive, key-rotation feature, server write amplification, or schema change was introduced.

Follow-up verification is in `.generated/e2ee-quality-audit/`: **4,283 unit tests across 409 files**, **707 local Worker integration tests across 85 files**, production build, both TypeScript targets, lint (two existing deprecation warnings), dead-code and unchanged bundle budgets pass. ## Changes from this audit

- **Damaged Reading caches no longer block healthy work.** An unreadable article could previously break another article's cache write or a library refresh. Reads now isolate undecodable records while preserving their original bytes. An unreadable library snapshot produces a recovery issue and allows the verified live library to open without overwriting the saved snapshot or pruning its articles. An unreadable target article cannot be silently replaced. Transaction/storage failures still surface, and drafts and pending edits remain protected.
- **Unchanged Reminders refreshes use one inventory request.** The client validates the first page, encryption generation and session before comparing the cached ETag. An unchanged library no longer fetches every inventory page. Changed libraries still paginate and confirm the final sequence before publication. This reduces reads and network traffic; it does not change write accounting.
- **Settings report Reading encryption separately.** A Reading-only device previously left the shared Encryption panel showing Reminders' checking state. Each feature now reports its own state, and Reading identifies its unlocked folder without implying notification enrollment.
- **The server candidate advances to revision 5.** Published releases use revision 4; reusing that revision for different stable server contents would prevent a safe update. Schema 2 and its released migration remain unchanged. The ordinary revision gate passes without overriding its baseline. The CSS budget was adjusted for mainline's shared list styles; all built bundles remain within their checked budgets.
- **New mainline behavior has encrypted integration coverage.** Tests verify that an empty vault adopts remote encrypted `.obsidian` settings without uploading its setup defaults, and that pending diffs and history comparisons decrypt retained baselines while preserving unsynced local edits. Reading tests verify highlights, annotations, tags and archive updates across clients, exact retry ciphertext after an accepted response is lost, and absence of those private values in server objects and receipts.
- **Encrypted folder moves are supported.** Ordinary file moves keep using conditional encrypted sync. Renaming an enrolled Reading/Reminders folder or its parent, or selecting a different configured folder, uses a durable, resumable scope conversion. Existing keys and the recovery code stay unchanged. Old and new prefixes, retained versions, policies and pending upload/restore receipts are handled together; unrelated file objects remain unchanged. Fresh browser setup links are required after a scope move. Rapid renames remain ordered, and an explicit authenticated server-settings recovery resolves conflicting device mappings while preserving local files. Content-key rotation was excluded at the user's request.
- **Fresh browser links accept moved folders without losing local encryption keys.** Previously, a browser with saved keys rejected its scope's new path. A newer generation with unchanged key identities can now update that path while preserving the wrapped local secret. Older links, same-generation path substitutions and path changes with different key identities remain rejected. Cached data and pending edits remain decryptable; they are not silently replayed into a new folder.

## Reviewed safety boundaries

Browser enrollment contains only its folder authority, never the whole-vault key. Keys travel in URL fragments and are removed before startup. Missing/damaged keys lead to recovery without discarding pending work. Content writes use authenticated encryption and conditional replacements; immutable attempts preserve ciphertext and operation identity across lost responses. Changed inventory snapshots are rejected before publication.

Reading plaintext content/capture/retry/handoff routes and server extraction are gated whenever encryption exists. Conversion includes current and retained content, queued captures and operation receipts before activation; derived plaintext indexes/jobs and old grants are removed. Adding Reading and moving existing scopes use resumable scope-generation conversions. Scope moves preserve all keys and purposes and retain original authenticated descriptors until replacements finish. The folder-connection follow-up above preserves browser sessions/subscriptions for renames; selecting different content still revokes them. Content-key rotation is not included.

Destructive reset clears Reading tables and grants at both boundaries so old capabilities cannot republish after the wipe. Shared logout clears keys and local private data with identity fences; partial cleanup failures are reported and cannot delete a newer enrollment. Unreadable/future-format records remain available for explicit recovery export.

Paths, approximate sizes, revisions, change timing and session/feature metadata remain visible. Reminder IDs, completion and due times remain disclosed for scheduling. Existing Reading filenames are preserved; new encrypted captures use generic names. The PWA trusts JavaScript served by its origin. Local vault files, old device copies, external backups and provider snapshots are not retroactively encrypted or securely erased. Explicit recovery exports may contain readable data. See [implementation](e2ee-implementation.md) and [Reading details](reading-e2ee-assessment.md).
