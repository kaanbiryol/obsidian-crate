# Crate documentation website

Astro Starlight builds the documentation at `/docs/`. The existing landing pages,
OAuth callback, privacy page, and shortcut downloads remain in `site/`. GitHub
Pages serves the combined static output; no Astro or Node server is deployed.

## Local development

Use the repository's Node version and npm. From the repository root:

```sh
npm ci
npm --prefix docs-site ci
npm run dev:docs
```

The docs development server prints its address with the `/docs/` base path.
Pagefind search is generated by the production build, so use the combined static
preview to test search and links between the landing page and documentation:

```sh
npm run check:docs
npm run build:site
python3 -m http.server 8080 --bind 127.0.0.1 --directory site
```

Open `http://localhost:8080/docs/`. The Canvas design is the main website at
`http://localhost:8080/`. Its former `/website-options/canvas/` URL redirects to
the homepage. Edit `site/index.html` for landing-page content; its styles remain
in `site/website-options/canvas/` and `site/website-options/studies.css`.

## Write user guides

Edit Markdown or MDX in `src/content/docs/`. Each page needs `title` and
`description` frontmatter. Use one topic per page, task-oriented instructions,
and links to a useful next step. Start headings at `##`; Starlight supplies the
page title. Keep current behavior separate from features in development.

Write for people using Crate, with setup and everyday tasks before implementation
details. Use the actual UI labels in bold and arrows for navigation. When documenting
a switch, explain its default, where to find it, which devices it affects, and what
turning it off preserves or stops. Verify these against the settings UI and runtime,
not just older documentation.

The user guide has four paths: getting started, using Crate, troubleshooting, and
the collapsed developer reference. Keep practical limits in
`src/content/docs/getting-started/limits.md`, with brief reminders next to the tasks
they affect. Feature settings, notification setup, and web app use each have their
own page under `src/content/docs/features/`. Link to those pages instead of repeating
their full setup steps. Keep protocol numbers, database details, and operator
procedures in the reference unless users need them to make a decision.

`astro.config.mjs` controls sidebar groups and order. Unlike Fumadocs, this setup
does not need `meta.json` files. Internal documentation links include `/docs/`
and a trailing slash. Pages use Starlight's navigation, theme controls, search,
and table of contents; `src/styles/custom.css` supplies Crate's colors and type.

Navigation uses native cross-document view transitions with an instant swap,
so supported browsers keep the current page visible until the next is ready.
There is no page fade or client-side router. `src/components/Head.astro` paints
the theme background early; browsers without view-transition support retain
normal links, search, and browser history. When changing navigation, check
sidebar links, search results, back/forward, and mobile menus in both themes.

## Maintain developer reference

The selected technical documents in root `docs/` remain the source of truth.
`scripts/prepare-reference.mjs` copies the pages listed in `scripts/reference.mjs`
into an ignored content directory before development, checking, and building.
Do not edit or commit those generated copies.

The Markdown plugin rewrites links between published references to `/docs/`
routes. Links to other repository documents or source files still go to their
GitHub paths. Edit-page links point to the canonical source. Implementation plans
are not automatically published or added to the sidebar. After changing a root
reference during development, run `npm --prefix docs-site run prepare:reference`
again to refresh it.

## Validation and deployment

`npm run check:docs` checks Astro and TypeScript. `npm run build:site` builds the
existing styles and docs, creates the local Pagefind index, and checks built
documentation links, anchors, assets, and landing-page links to the docs.
Generated files go only into the ignored `site/docs/` directory.

The existing Pages workflow installs the separate lockfile, checks and builds
the site, and uploads `site/`. Pushes to `docs-site/` or `docs/` also trigger it.
Local builds do not deploy anything.

For a dependency review, run `npm --prefix docs-site audit`. As of 2026-10-03,
Astro pulls in `http-cache-semantics` 4.2.0, which has an unpatched advisory
([GHSA-ch52-4w7c-c8xp](https://github.com/advisories/GHSA-ch52-4w7c-c8xp)) about
shared HTTP caches. This project publishes static files, uses local assets,
and deploys no Astro runtime or shared response cache. The audit still reports
the dependency finding; it has not been suppressed. Reassess it when updating
dependencies or introducing remote assets or server rendering.
